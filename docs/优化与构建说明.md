# 直方图（Make Graph）性能优化与构建运行说明

> 适用范围：`Singan2_Lai_GBVE_SR_AI`（Web 重构工程）。
> 配套源码：`server/server.cpp`、`web/src/App.jsx`、`web/src/components/MakeGraphRow.jsx`。
> 关联脚本：`run_all.bat`（一键构建+启动）、`build_core.bat`（首次 cmake 配置）。

---

## 1. 问题背景

在 Web 端点 **Make Graph**（直方图）分析大量图像（例如 1000 张）时，后端单次请求耗时可达 ~30s，
前端长时间无响应。

### 1.1 耗时根因（已定位）

直方图绘制本身极快（`/api/graph/make` 返回的 `rows` 仅做整数分箱，亚毫秒级）。
真正的瓶颈在 **per-record 的特征计算**：

- 后端 `/api/graph/make` 处理函数（运行在 httplib 线程池的某个 worker 线程上）内，对展开出的每个 record
  串行调用 `make_graph_record()` —— 读图 + 字节转换 + `ALL32` 32 维特征计算。
- 单图约 10–30ms（单线程），1000 张串行累计 ≈ 10–30s，与实测吻合。
- 这段是**单线程顺序**代码：多核 / 高主频都用不上，加 CPU 不会自动加速。

### 1.2 关于「257 张以后怎么显示」的澄清

早期误以为工程内有 `max_records=256 / Step / Start` 的 256 上限（那是按“应如何实现”的猜测，并非本工程真实逻辑）。
实际本工程原本**没有 256 上限**——`max_records` 由前端传入、后端原未封顶。
本次优化**显式引入 8192 上限**（见 §2），并把前端默认 `Times` 自动填为全部图像张数，
因此「全部图像都进直方图」这一诉求已满足，8192 之外的超大样本（>8192 张）会被截断并提示。

---

## 2. 优化方案

### 2.1 后端：per-record 计算并行化（`server/server.cpp`）

`/api/graph/make` 处理流程：

1. 按 `start_record / step / max_records` 展开本次要处理的 record 序号，越界即止（`server.cpp:860-867`）。
2. `max_records` 上限封顶 **8192**（`server.cpp:918`）。
3. 用 `std::thread` 线程池并行执行各 record 的计算（`server.cpp:872-899`）：
   - 线程数 = `std::thread::hardware_concurrency()`，超过 record 数时取较小值；
   - 按 `chunk = (m + nthreads - 1) / nthreads` 均分区间，每线程只写自己的下标 `values[i] / ok[i]`，**无数据竞争**；
   - `make_graph_record()` 内部持有局部 `ImageEngine`，文件读取走**带锁的 LRU 缓存**，跨线程共享读不冲突。

效果：1000 张在 N 核机器上近似变为「单张耗时 / N」，20–30s → 约 2–5s（取决于核数）。

### 2.2 前端：Times 自动覆盖全部图像（`web/src/App.jsx`）

打开数据（`openSession`）成功后，批量参数默认对齐“分析全部图像”：

```jsx
// App.jsx:206-209
setMgStart(0);
setMgStep(1);
setMgTimes(Math.min(s.record_count, 8192));   // 自动填为图像张数，封顶 8192
```

`MakeGraphRow.jsx` 的 Times 输入框带 `title` 提示「默认已自动填为全部」，并显示 `/{total}` 总数。

> 注：原 OLD MFC 工程默认 `Start/Step/Times = 10/10/5`，属抽样模式；本次 Web 端为“看全部图像”改默认全量。
> 如需抽样，手动改 Start/Step/Times 即可。

## 3. 构建与运行

### 3.1 一键启动（`run_all.bat`）—— 推荐

`run_all.bat` 已**内联编译步骤**，双击即可完成「杀旧进程 → 增量重编 → 起后端 → 起前端」：

```bat
REM run_all.bat 关键行
"%CMAKE%" --build "%ROOT%\build" --config Debug --target singan2_server   :: 第48行，增量重编
start "SINGAN2-API" "%SERVER_EXE%" %PORT_API%                            :: 后端 :8080
start "SINGAN2-WEB" cmd /k "cd /d %ROOT%\web && npm run dev"            :: 前端 :5173 (Vite 热更新)
```

- **改完 `server.cpp` 后，直接重跑 `run_all.bat` 即可自动重编并重启**，无需手动 cmake。
- 前端改动经 `npm run dev` 热更新即时生效（无需重启 bat）。
- 首跑前需先运行 `build_core.bat` 生成 `build/CMakeCache.txt`（bat 第43-47行有检查，缺失会提示）。

### 3.2 Debug vs Release

| 配置 | 路径 | 说明 |
|------|------|------|
| **Debug**（run_all.bat 默认） | `build/server/Debug/singan2_server.exe` | 默认；并行化多核生效，够用 |
| Release | `build/server/Release/singan2_server.exe` | 优化编译，单 record 更快，整体更优 |

`run_all.bat` 默认走 **Debug**（第12、48行写死 `Debug`）。若要最快速出图，可把这两处 `Debug` 改为 `Release`
（本机 `build/server/Release/` 已存在可用产物）。手动编 Release：

```bat
cmake --build build --config Release --target singan2_server
```

### 3.3 手动分步构建（备用）


## 5. 服务端并发模型（请求级线程池）

### 5.1 httplib 默认即多线程

`cpp-httplib` 的 `Server` 默认构造函数即建立线程池：

- 基础线程数 `base = max(8, 硬件线程数 - 1)`；
- 最大线程数 `max = 4 × base`（空闲线程超时自动回收，峰值可动态扩容）。

因此**服务进程默认就能并发处理多个 HTTP 请求**——例如上传 655MB 大文件（约 6.5s）期间，
前端同时发来的「取图 / Make Graph / 打开数据」等请求会在其它 worker 线程上并行执行，不会被上传阻塞。
（注：单条请求 handler 内部仍是单线程顺序执行；其中 Make Graph 的 per-record 计算已由 §2.1 的 `std::thread` 进一步并行。）

### 5.2 显式声明（server.cpp）

为让并发意图清晰、并集中在一处便于调参，`server.cpp` 在 `svr.listen` 前显式声明（参数与 httplib 默认完全一致，仅显式写出，可按机器核数调大 `base`）：

```cpp
svr.new_task_queue([] {
    const size_t base = (std::max)(8u, std::thread::hardware_concurrency() > 0
                                          ? std::thread::hardware_concurrency() - 1
                                          : 0);
    return new httplib::ThreadPool(base, base * 4);
});
```

### 5.3 线程安全前提（已满足）

并发生效的前提是 handler 间无共享可变状态竞争，本工程已满足：

- **WTable 缓存**：`get_wtable()` 内 `static std::mutex mu` 保护 `std::map` 读写（server.cpp:336-356），多请求并发取表安全。
- **ImageEngine**：每个请求在处理函数内**本地构造**（`ImageEngine eng;`），从磁盘读取 `dat_path`，不跨请求共享。
- Make Graph 的 per-record 并行（§2.1）各自持有局部 `ImageEngine`，文件读走带锁 LRU 缓存，无数据竞争。

### 5.4 上传吞吐实测（流式写盘 + 线程池）

大文件走 `/api/upload` 流式分块落盘，经 Vite 代理实测：

| 文件 | 大小 | 耗时 | 速率 |
|------|------|------|------|
| 12_100_D.dat | 286MB | ~4.7s | ~61 MB/s |
| 12_100D_C.dat | 655MB | ~6.5s | ~100 MB/s |

内存恒定在几十 KB（仅一个写缓冲），不随文件变大；上传上限已放宽到 4GB（见 `server.cpp` 的 `set_payload_max_length`）。

### 5.5 大响应体传输加固：`TCP_NODELAY`（防御性，非 11s 根因）

**现象**：`POST /api/images/channel` 返回 17MB 整通道像素，早期用某 Python 测量客户端测到 ~11 秒；但 `extract_wave_all` 服务端分段计时显示拷贝仅 8–15ms。

**真相（已复核）**：~11 秒是**测量客户端自身的 bug**——接收循环用 `data += chunk` 对不可变 `bytes` 做 O(n²) 累加（17MB 累积约 37GB 内存搬移）。用流式落盘的正确客户端重测，17MB 下发实测 **~80ms**，服务端无任何瓶颈。详见 [13_性能优化_整通道预载与秒级加载.md §1.3](./13_性能优化_整通道预载与秒级加载.md)。

**加固**：`server.cpp` 在 `svr.listen` 前加 `svr.set_tcp_nodelay(true);`（关闭 Nagle，避免大响应体在个别网络路径上因 Nagle+延迟ACK 相互等待降速）。它不是 11s 的修复点，但是对远端/高延迟部署无副作用的稳妥加固，保留。

**生效前提**：本加固在 `server.cpp`，**必须重编 `singan2_server`** 才能生效（前端 HMR 不覆盖）；重编见 §3。本工程仅本地单机使用，关闭 Nagle 无副作用。
