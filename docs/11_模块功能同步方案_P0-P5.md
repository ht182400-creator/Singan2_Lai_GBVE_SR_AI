# 11_模块功能同步方案（P0–P5）

> 目标：让 Web（`Singan2_Lai_GBVE_SR_AI/web`）的功能与原版 MFC（`Singan2_Lai_GBVE_SR_OLD`）逐模块对齐。
> 前置状态：UI 复刻约 90%（见 `Web_UI_1to1_视觉模型对照清单.md`），算法层 C++ 移植已对拍通过（M0/M1/M2，18/18）。
> 创建日期：2026-09-01

---

## 0. 结论速览

| 项 | 结论 |
|---|---|
| MFC 功能规模 | 主窗口 `WinMain.cpp` 约 50 个 `case IDC_*`；另含 20+ 国家算法、图像处理算子、ATB/VTB、图表、保存导出 |
| Web 当前功能 | **接近 0**——`web/src/api.js` 无任何 import，全站零网络请求；所有按钮只 `pushHistory()` 记日志 |
| 后端当前能力 | 仅 1 个：`run_algorithm` → `{s2[33], etc[15]}` |
| 最大瓶颈 | 不是算法（算法已移植且对拍通过），而是 **①后端 API 太薄 ②core 能力未暴露 ③Web 无数据层** |
| 执行顺序 | P0 基础数据链路 → P1 分析 → P2 图像处理 → P3 Graph → P4 ATB/VTB/坐标 → P5 保存与配置 |

## 1. MFC 原版功能结构（对齐基准）

### 1.1 分层与主流程

```text
UI 层      WinMain.cpp DialogProc
             ├─ WM_COMMAND   ~50 个 case IDC_*（按钮/菜单）
             ├─ WM_HSCROLL   滑块（Image Processing 参数）
             ├─ WM_DRAWITEM  图像绘制
             └─ WM_DROPFILES 文件拖放
              ↓
编排层      MainRun.cpp   MainRun / MainRun1 / MainRun2 / ReadImgDataNew / funDatas1-2
              ↓
分派层      ALL32.CPP     ALL32 → InitAll32 → 公共特征(C_SI2) → switch(国家) → 国家函数
              ↓
数据层      CTemplateData / CFileAccess / CDataHeader / CTemplateVTB
              ↓
算法层      C_SI2.CPP(32 维特征) / GRADIENT / PREWITT / LAPLACIAN / NITI /
           smooth_median / To2byte / bvmath(Rute 整数开方)
```

主流程：`读 .dat → ReadImgDataNew → MainRun → ALL32 → 国家函数 → S2[1..32]`

#### P3 Web 端算法（2026-09-01 新增，复刻 OnDrawPaint.cpp / OnDrawGraph.cpp）

- **数据来源**：`/api/graph/make` 返回跨 record 的 `rows`，前端按 `graphFn`（1..44）取函数列值。
- **分布与统计**：`web/src/utils/graphStats.js`
  - `buildDistribution` 把相同值分组（记录 1-based record 号）；`avgDev` / `stdDev`（÷n-1）/ `sigmaCompute` 对齐 OLD `gr_per()` 与 `DrawGraphBoth`。
  - `distributionToText` 输出 OLD 风格列表 `值 ( count ) <= rec,...`。
  - `buildGraphStats` **单数据源复刻 OLD 同文件场景**：Graph1/Graph2 均取自全部 `rows`，仅由 `include1/include2` 控制是否绘制，故 IR1/IR2 为同一文件时绿/蓝柱状图完全重叠；后续若支持双文件对比再引入 file1/file2 分桶。
- **绘图**：`GraphPlot.jsx` 改为**直方图**（横轴=value、纵轴=count），file1 绿色、file2 蓝色竖线；右侧显示 Avg/Std/Min-Max/Gap/Middle/Sig。
- **列表**：`App.jsx` 的 `Graph1`/`Graph2` 编辑框在 Make Graph 有数据时显示分布列表，否则回退单条 s2/etc。
- **参数映射**：1/2 → `mgInclude1/2`；Black/White → `mgBw`（仅标题标记）；+Area/+TH → `mgArea/mgTh`（标题显示开关）；Start/Step/Times → `mgStart/mgStep/mgTimes`；1<2 → `mgCmp12`（Gap 方向）。
- **Mouse Point 实时宽高**：`ImagePane.jsx` 在 `freeHand` 拖拽期间通过 `onSizeChange({w,h})` 持续刷新 `App.mouseSize`（对应 OLD `Freemove_mouse` 持续写 `IDC_M_WIDTH/HEIGHT`），mouseUp 时再通过 `onSelect({x1,y1,x2,y2})` 确认。
- **Make Graph 真实语义修正（2026-09-02）**：`/api/graph/make` 改复刻 `CreateGraph1 + ComputeSuppleResult`，返回每 record 在选区内的黑/白像素数 `rows[].value`，并透传 `wave`/`niti_type`/`grad_type`/`gain`/`threshold`/`color_point`/`area_*`/`black`；`graphStats.js` 新增 `getGraphValue` 兼容像素统计与 S2/ETC；S2Chart 改由 Statistics 批量数据 `batchStats.all` 提供，与 Make Graph 解耦。
- **验收**：`npm test` 31 文件 / 160 用例全绿；server Release 编译通过；`read_lints` web 0 错误（server.cpp 头文件路径告警为既有环境配置问题，非本次改动引入）。
- **待补**：`+Area`/`+TH` 实时重算（接鼠标/阈值事件）。

## 6. 执行约定

1. **算法不下放到 TS**：所有数值计算留在 C++ core，Web 只做展示与交互，避免引入数值偏差。
2. **新增能力先加 core，再加 server 端点，最后接 Web**：保持"能力→接口→界面"的单向依赖。
3. **每阶段结束跑对拍与 `npm test`**：前端改动不得破坏既有 117 条测试。
4. **未移植模块明确标注**：P3–P5 中依赖未移植 MFC 模块的部分，接口可先返回可用结果，但必须在代码与本文档标注 `[需补移植]`。

### 7.11 第九轮（2026-09-02）：Statistics 慢——根因与优化（批量分析端点）

- **用户追问**：Statistics 为何慢、上限 200？能否优化？为什么要发 200 次请求？
- **根因**：原 `runStatistics` 在循环里对每条 record 串行 `await analyzeByPath`（单次 `/api/analyze-path`），即 200 次 HTTP 往返；每次还会在后端重复 `parse_blocks` + `gen_w_table` + `parse_zahyo_param` + 重建 ImageEngine，且前端串行等待，所以既慢又产生大量请求。
- **优化方案**：新增服务端批量端点 `/api/analyze-batch`（一次请求带 `start/step/count`，服务端按 `start/step` 展开取样序号后**内部多线程并行**计算 ALL32，一次返回 `results:[{record,s2,etc}]`），把 200 次 HTTP 压缩成 1 次，并复用同一文件缓存、并行利用多核。
  - `server.cpp`：在 `/api/analyze-path` 后新增 `svr.Post("/api/analyze-batch", ...)`。`n = min(count, available, 200)`（`available` 为本文件在 `start/step` 下不重复记录数，避免小文件重复），并行 worker 复用 `graph/make` 的线程分块范式；单条失败写入 `error` 字段不中断整体。
  - `web/src/api.js`：新增 `analyzeBatchByPath({datPath,zfilePath,start,step,count,kin,country})`。
  - `web/src/App.jsx`：`runStatistics` 的 `computeBatch` 改为 `await analyzeBatchByPath(...)` 后遍历 `resp.results` 归一化，仅在异常无结果时提前返回。
- **验证**：
  - 重编 `singan2_server`（Debug）：成功。
  - 启动后端实测：`/api/analyze-batch` 传 `count=5` 返回 `count=5, record_count=40, results=5, s2.length=33`，正确。
  - `npm test -- --run`：**33 文件 / 173 用例全绿**；`npm run build` 通过；`read_lints` 0 错误。
  - 效果：Statistics 的网络往返从「1 次/record」降为「1 次/文件」；服务端并行后 CPU 密集的 ALL32 计算也明显加速。仍保留 `STATISTICS_MAX_RECORDS=200` 作为单文件取样上限以防后端单次 payload 过大。

### 7.21 第十九轮（2026-09-03）：Graph 操作区语义分析 + 1:1 重建（Mul-X/ABS 为原版死控件）

#### 一、OLD 参数语义分析（用户问：这些参数是 Make Graph 用还是 VTB 用？）

**结论：全部属于 Make Graph（图表测量），与 VTB 无关。** 依据 `MainRun.cpp CreateGraph1(:2556)/CreateGraph2(:2936)`。

**1. 函数列表 `IDC_LIST_GRAPH_FUNS`（991,280,106×60）—— 测量方法选择器**
- 初始填入（WinMain:847）：`0 - Sum pixels / 1 - width / 2 - height (TBD) / 3 - differenct neighbour / 4 - (TBD)`
- `CreateGraph1/2` 对每个 record 调 `ComputeSuppleResult(oneimg, resultMethod, pts, mouse_range_point, &blacks, &whites, threshold)`（MainRun.cpp:2723），`resultMethod = LB_GETCURSEL`（未选默认 0）：
  - **case 0（Sum pixels）**：选区内逐像素 `color + (global_color_point - 150)` 截断 [0,255]；`==0` → black++，`==255` → white++。
  - **case 1（width）**：选区内黑(0)/白(255) 的**水平跨度**：从左向右找第一列含黑 → blackLeft，第一列含白 → whiteLeft；再从右向左找 blackRight/whiteRight；`width = |R - L| + 1`。
  - **case 2（height）**：**空实现**（原版即 TBD，返回 0）。
  - **case 3（differenct neighbour）**：选区内水平 `|img[j][i+1]-img[j][i]|` + 垂直 `|img[j+1][i]-img[j][i]|`，**> 阈值（二值化滑条值）才累加**，总和封顶 65535，`black = white = sum`。注意 OLD 中 method 0-2 调用时传 `threshold=0`，只有 method 3 用真阈值。
  - **case 4**：无 case（不执行）。
- 结果写入 `global_graph1/2_black[record]` 与 `_white[record]`，即 Make Graph 曲线数据。
