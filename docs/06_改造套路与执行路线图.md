## 1. 核心思路（一句话）

> 先搭**验证工程（POC）**，把"算法能否脱离 Win32 独立复现"这个最大假设，用「同数据 → POC 输出 vs 原版 exe 输出」的对拍结果验证掉，**再决定走 Web 化还是原生优化**。

### 为什么必须先验证

- 这个项目算法层（`C_SI2` / 各国算法 / 图像处理）是纯 C/C++，理论上可脱离 Win32；
- 但"理论上可移植"与"实际能跑出一模一样的 `S2[1..32]`"之间，隔着**数据解析正确性**和**数值语义一致性**两道坎；
- 不先验证就贸然投入 Web 化或大规模重构，一旦解析有偏差，全部工作作废。

## 3. 三条改造路径与选择逻辑

### 3.1 为什么是这三种路径

C++ 算法无法在浏览器/JS 环境直接执行，解决矛盾只有两类手段，再加一条绕开客户端的路：

```
C++ 算法代码必须跑在某个 CPU 上
│
├── 浏览器端（客户端本地算）
│     ├── 编译执行 → A. WASM（Emscripten 编译 .cpp → .wasm）
│     └── 翻译执行 → B. TypeScript 重写（手工逐函数翻译）
│
└── 服务端（Node 进程算）
      └── 编译成 Node 插件 → C. Node N-API（.node 插件）
```

- A/B 是"编译 vs 翻译"，**完备覆盖浏览器端**；
- C 回答"不在浏览器跑、不翻译"时如何复用 C++（仍是编译，目标换为 Node 进程）；
- 三者是"**在哪儿跑 + 怎么复用 C++**"两个决策维度的自然组合，构成完整决策空间。

### 3.2 排除的方案及理由

| 方案 | 为何排除 |
|---|---|
| asm.js | WASM 前身，同样靠 Emscripten，直接上 WASM |
| Python 后端 | 算法源是 C++，翻译一遍风险同 TS，且无复用价值 |
| 原 exe 包 HTTP 壳 | C 类的简化变体，依赖 Windows + 进程管理 |
| Electron 桌面壳 | 本质还是桌面应用，非 Web 化 |
| 在线通用 AI/API | 私有算法（几十个国家特征公式），无法用通用服务替代 |

### 3.3 推荐结论

| 场景 | 首选 | 理由 |
|---|---|---|
| 需要算法行为与原版**完全一致**的验证/分析工具 | **A. WASM** | 原码直接编译，消除翻译引入的数值偏差 |
| 无 WASM 构建链、全栈 TS 团队 | B. TS 重写 | 免去工具链，但需处理定点运算语义（`Math.imul`/`>>>0`） |
| 服务端集中批量处理 / 多用户共享数据 | C. Node N-API | 计算集中、数据集中管理 |

## 4. 验证工程（POC）设计

### 4.1 POC 要回答的 3 个问题

| # | 问题 | 判定标准 |
|---|---|---|
| Q1 | 算法层能否完全脱离 Win32 独立跑通？ | POC 不链接任何 Win32 头/库，纯 C/C++ 编译通过 |
| Q2 | 提取的解析逻辑与原版输出是否一致？ | 同一枚 `.dat` → `S2[1..32]` 逐项 == 原版 exe 输出 |
| Q3 | 单枚数据处理性能如何？ | 记录耗时，作为 Web 化 / 优化的性能基线 |

### 4.2 架构与步骤

```text
步骤1：抽取算法文件（不链接 Win32）
        C_SI2.CPP / GRADIENT.CPP / PREWITT.CPP / LAPLACIAN.cpp / NITI.CPP
        smooth_median.cpp / To2byte*.cpp / bvmath.cpp / ALL32.CPP
        国家文件（Euro/Chia/USA/...）/ CTemplate*.cpp / ReadImgData（摘逻辑）

步骤2：全局状态封装
        MAIN.H 的 global_*（约90个）打包为 Context 结构体，
        POC 阶段先保留为全局变量（最小改动），仅保证"无 HWND/无 GDI"

步骤3：去 HWND
        删除国家函数与 UI 包装函数的 HWND 形参及 GetDlgItemInt/SendMessage 分支

步骤4：文件 I/O 抽象
        fopen/fread → 读入内存缓冲 + 偏移切片（对齐浏览器 fetch/File API）
        CFileAccess 的 CreateFile/ReadFile → 替换为内存读取

步骤5：纯 C 控制台主程序
        main()：读 .dat + 坐标文件 + GBV_DIV_H.bin → 单枚处理 → 打印 S2[1..32]

步骤6：对拍
        原版 exe 对同一枚数据跑一遍 → 导出 S2 → 与 POC 输出逐项比对
```

### 4.3 输入与输出

| 项 | 说明 | 来源 |
|---|---|---|
| `.dat` 数据文件 | MarinerFormat 格式，原版 exe 能正常读 | 用户提供 |
| 坐标文件 `.bin.txt` | 各币种/面额区域坐标参数 | 用户提供 / si2 中指定 |
| `GBV_DIV_H.bin` | 除法表（`w_Table[16384]`） | 仓库根目录已有 |
| 原版 exe 的 S2 输出 | 对拍基准 | 用户在本机跑原版导出 |
| POC 输出 | `S2[1..32]` + 单枚耗时 | 本工程 |

### 4.4 验收标准

1. ✅ POC 纯 C/C++ 编译通过，**不链接任何 Win32 库**；
2. ✅ 同一枚数据，POC 的 `S2[1..32]` 与原版 exe 输出**逐项一致**（整型精确相等）；
3. ✅ 单枚处理耗时记录完成（作为基线）；
4. ✅ 差异项（若有）逐条登记原因（解析偏差 / 数值语义 / 原版自身 BUG）。

## 5. 决策树（POC 之后的分流）

```
POC 对拍结果
│
├─ Q1 失败（算法层有隐藏 Win32 依赖）
│    └→ 定位依赖 → 评估剥离成本 → 决定 Web 化 或 放弃改造
│
├─ Q2 不一致（S2 有差异）
│    └→ 逐项排查（解析偏移 / 字节序 / 定点溢出 / 原版 bug）
│        ├─ 修好后再评估
│        └─ 若为原版 bug → 单独记录，决定是否以 POC 为准修正
│
└─ Q1、Q2 全通过（核心假设成立）
     ├─ 目标 = Web 分析工具 → 走路径 A（WASM），UI 重写
     ├─ 目标 = 服务端批量 → 走路径 C（Node N-API）
     └─ 目标 = 优化原生工具 → POC 工程即回归基准，直接做优化
```

## 7. 验收 / 回归机制（对拍方法论）

这是整套套路的**基石**，所有后续改动都必须过这道闸：

### 7.1 对拍流程

```text
同一枚数据
   ├─ 原版 exe → 导出 S2[1..32]（基准）
   └─ POC/Web/优化后 → 导出 S2[1..32]
              ↓
   逐项比较，要求整型精确相等
              ↓
   有差异 → 记录差异表（索引 / 原值 / 新值 / 原因 / 结论）
```

### 7.2 差异处理规则

| 差异类型 | 处理 |
|---|---|
| 解析偏移错误 | 修正 `CTemplateData`/`ReadImgData` 逻辑，回归 |
| 数值语义（溢出/定点） | WASM 路径不存在（原码编译）；TS 路径用 `Math.imul`/`>>>0` 修正 |
| 原版 exe 自身 BUG | 单独记录为已知差异，不在本次改造内修复 |
| 无法判定 | 冻结该枚数据，换数据再对拍，绝不跳过 |

### 7.3 回归触发条件

- 每次修改算法/解析/全局状态代码后，**必须**跑对拍；
- 新增一枚数据 = 新增一组对拍用例；
- 对拍结果与测试用例文档**一一对应**（遵循项目规则）。

## 11. 优化改造方向：日文 → English（2026-08-20 决策）

> 用户明确要求：后期优化改造时，**把界面与代码中的所有日文改成英文**。
> 本决策需在 POC 算法对拍收敛后再执行，避免在移植阶段引入额外变量。

### 11.1 日文分布现状（待改范围）

| 类别 | 文件/位置 | 现状 |
|---|---|---|
| **界面文案** | `resource.rc`、`SetManual.cpp`、`WinMain.cpp` | 按钮/标签/菜单大量日文（如"すかし""赤外""緑""汚れ"） |
| **日志/提示** | 各 .cpp 的 `MessageBox` | 弹窗文案为日文（Shift-JIS 编码） |
| **坐标文件** | `X_ATB_*.txt` | 段标题为日文（`【すかし１】`、`【Thread】`、`【IR 1】` 等） |
| **注释** | 各 .cpp/.h | 日文注释（`// 併嶼` 等） |
| **CSV 输出** | `WinMain.cpp:1230` | 每行第 1 列 `%5d枃栚`（日文"枚目"） |
| **文件名** | `GBV°æ_DIV_H.bin` | 含日文（°æ） |

### 11.2 改造原则

1. **先收敛算法对拍，再动文案**：日文改动不改变任何数值逻辑，但会动到 `resource.rc`/`SetManual.cpp` 的 **Shift-JIS 编码**，风险高，务必排在算法稳定之后。
2. **编码安全**：涉及 Shift-JIS 的文件（`SetManual.cpp`、`resource.rc`、`GBV°æ_DIV_H.bin`）必须用 `[Text.Encoding]::GetEncoding(932)` 转码，**严禁用 UTF-8 文本工具直接编辑**（会破坏字节且不可恢复）。
3. **全量替换**：界面文案、日志、注释、CSV 表头一次性全部替换为英文，避免中英/日英混存（遵循"统一风格"规则）。

### 11.3 建议的英文命名映射

| 日文 | 英文 |
|---|---|
| すかし（透かし） | Watermark / Sukashi（若保留内部名可用 `Sukashi`） |
| 赤外 | Infrared |
| 緑 | Green |
| 汚れ | Dirt / Stain |
| 枃栚（枚目） | Index / No. |
| 図（ず） | Image |
| 設定 | Setting |

> 坐标系文件段标题（`【すかし１】`→`Watermark1` 等）的改名**会影响 `ReadZFile` 的文件头判断**，必须在确认算法对拍全部通过后再改，且 POC 的 `zahyo_reader.py` 需同步更新段标题匹配。
