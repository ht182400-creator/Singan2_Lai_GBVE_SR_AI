# 07_项目开发规范与角色职责

> 本规范是 `Singan2_Lai_GBVE_SR_AI` 项目（SINGAN2 改造工程）的**开发总纲**。所有进入本目录的代码、文档、日志、测试，均须遵守本规范。以**架构师 / 产品经理 / UI 设计师 / 全栈工程师 / 测试专家 / 文档专家**六角色标准严格要求。

---

## 1. 总则

### 1.1 项目定位

| 项 | 说明 |
|---|---|
| 项目名 | `Singan2_Lai_GBVE_SR_AI` |
| 上游源码 | `Singan2_Lai_GBVE_SR_OLD`（只读基准，**禁止直接修改**） |
| 目标 | 基于上游算法，完成"验证工程 → 路线决策 → Web 化或原生优化"的改造 |
| 工作目录 | **所有改造产物（代码/文档/日志/测试）一律写入本目录** |

### 1.2 核心原则

1. **上游只读**：`Singan2_Lai_GBVE_SR_OLD` 是基准，只用于阅读与对拍，不在其中改代码。
2. **决策不做在验证之前**：任何技术路线决策，必须先有验证数据（见 `06_改造套路与执行路线图.md`）。
3. **规范先行**：写代码前先过规范；提交前先过自检；合并前先过评审。
4. **文档与代码同步**：改代码必须同步改文档，禁止文档过时。
5. **日志必写**：开发日志 / 运行日志 / 测试日志三层，缺一不可。

### 1.3 目录结构约定（规划）

```
Singan2_Lai_GBVE_SR_AI/
├── docs/                     # 文档体系（本目录）
│   ├── README.md             # 文档导航中心
│   ├── 01~06                 # 架构解读与评估文档
│   ├── 07_项目开发规范与角色职责.md   # 本文件
│   ├── 08_测试规范与用例管理.md      # 测试规范
│   ├── 09_原版导出S2对拍基准操作指南.md # 原版 exe 导出 S2 对拍基准操作（含实测截图）
│   ├── 10_界面与交互文档.md              # 界面结构 + Web 化目标设计（带图）
│   ├── 开发日志/               # 开发日志（YYYY-MM-DD.md，只追加）
│   └── 决策记录/               # ADR（架构决策记录）
├── poc/                      # M0 验证工程（纯 C/C++ 控制台，不链接 Win32）
```

## 2. 六角色职责与交付物

每个角色独立承担职责，产出对应交付物，并参与相应评审。

### 2.1 产品经理（PM）

| 项 | 内容 |
|---|---|
| 职责 | 需求收集与澄清、需求拆解、优先级排序、验收标准定义、里程碑规划 |
| 交付物 | PRD（产品需求文档）、需求清单、用户故事、验收标准 |
| 评审点 | 需求是否可验证、优先级是否合理、范围是否可控 |
| 本项目落地 | `06_改造套路与执行路线图.md` 的里程碑即需求基线 |

### 2.2 架构师（Architect）

| 项 | 内容 |
|---|---|
| 职责 | 总体架构设计、技术选型、模块边界、接口契约、数据流设计、风险控制 |
| 交付物 | 架构设计文档、接口定义（API 契约）、ADR（架构决策记录） |
| 评审点 | 方案是否满足非功能需求（一致性/性能/可维护性）、决策是否有据 |
| 本项目落地 | `01/02/05` 文档 + 后续 ADR |

**ADR 模板**：

```markdown
# ADR-XXX: <标题>
- 状态：提议 / 已接受 / 已否决 / 已取代
- 日期：YYYY-MM-DD
- 背景：<为什么做这个决策>
- 选项：<列出的候选方案>
- 决策：<选定方案>
- 理由：<数据/依据>
- 后果：<正面/负面影响>
- 关联：<相关 ADR / 文档>
```

### 2.3 UI 设计师（UI/UX）

| 项 | 内容 |
|---|---|
| 职责 | 交互流程设计、视觉风格、信息架构、可访问性、设计走查 |
| 交付物 | 设计规范（颜色/字体/间距/组件）、原型、设计说明 |
| 评审点 | 交互是否清晰、视觉是否统一、是否满足用户场景 |
| 本项目落地 | `10_界面与交互文档.md`（原版界面结构 + Web 化目标设计，带图） |

### 2.4 全栈工程师（Dev）

| 项 | 内容 |
|---|---|
| 职责 | 前后端代码实现、代码规范执行、单元自测、联调、性能优化 |
| 交付物 | 可运行的代码、编译/构建脚本、自测报告 |
| 评审点 | 是否符合代码规范、是否通过编译与自测、是否有回归 |
| 硬性要求 | **每次修改后必须：编译检查 + 导入测试 + 关键函数回归测试** |

### 2.5 测试专家（QA）

| 项 | 内容 |
|---|---|
| 职责 | 测试计划、用例设计（正常/边界/异常/分支/并发）、测试执行、缺陷管理、回归保障 |

| 评审点 | 覆盖率是否达标、用例与实现是否一一对应、缺陷是否闭环 |

### 2.6 文档专家（Doc）

| 项 | 内容 |
|---|---|
| 职责 | 文档体系维护、版本同步、新手指引、FAQ、发布说明 |
| 交付物 | 本目录全部 `.md` 文档、开发日志、README 导航 |
| 评审点 | 文档是否与代码同步、是否可检索、是否面向读者 |

## 3. 代码规范

### 3.1 通用规范

1. **函数上方必须有注释**（JSDoc 风格），复杂逻辑添加行内注释，注释用中文。
2. **禁止硬编码**：魔法数字、字符串、路径、超时、阈值等必须提取为常量（C++ 用 `UPPER_SNAKE_CASE`，JS/TS 用 `CONST_NAME`）并加注释。
3. **模块化**：单文件超过 500 行按职责拆分；内部模块用 `_` 前缀命名。
4. **统一风格**：选定一种风格后全局一致，禁止混用范式，禁止半途重构留下"版本幽灵"。

### 3.2 C/C++ 规范（POC / 原生 / WASM 核心）

```cpp
/** 计算指定区域的像素均值
 * @param x 起点 X
 * @param y 起点 Y
 * @param xx 终点 X
 * @param yy 终点 Y
 * @param img 图像缓冲
 * @param type 处理类型
 * @return 均值；失败返回负值
 */
long AverageConcentration(int x, int y, int xx, int yy, const USHORT* img, int type)
{
    // 参数校验
    if (img == nullptr || xx < x || yy < y) {
        LOG_ERROR("AverageConcentration 参数非法: (%d,%d)-(%d,%d)", x, y, xx, yy);
        return -1L;
    }
    // ... 实现
}
```

**C++ 具体规范**：
- 命名：函数 `PascalCase`；变量 `camelCase`；常量 `UPPER_SNAKE_CASE`；成员 `m_` 前缀；全局（尽量不用，用 Context）`g_` 前缀。
- 错误处理：**必须 try-catch / 返回码**，禁止静默吞异常；`LOG_ERROR` 必须含 `traceback`（C++ 用 `LOG_ERROR` 宏 + 上下文）。
- 指针：能 `const` 就 `const`；能引用就引用；禁止裸 `new/delete` 散落（RAII）。
- 头文件：`#pragma once`；接口与实现分离。
- 移植约束：核心算法层**不得包含 `<windows.h>` / GDI / DialogBox**，保证可编译进 WASM。

### 3.3 TypeScript / JavaScript 规范（Web 前端）

- ESLint + Prettier 统一；`strict: true`。
- 命名：组件/类 `PascalCase`；函数/变量 `camelCase`；常量 `UPPER_SNAKE_CASE`；类型 `PascalCase`。
- 组件规范：函数式组件 + Hooks；禁止类组件与函数式混用。
- 状态管理：单一数据流，禁止全局可变状态散落。
- 异步：`async/await` + try-catch，禁止裸 Promise 链与未捕获拒绝。

### 3.4 Git 提交规范

```
<type>(<scope>): <subject>

# type: feat / fix / docs / style / refactor / test / perf / chore
# scope: poc / web / native / docs / test / core
# 例：feat(poc): 完成单枚数据 S2 输出与对拍脚本
```

- 一次提交一个逻辑变更；禁止把无关改动混入一次提交。
- 提交信息用中文 subject，简洁描述"做了什么 + 为什么"。

### 3.5 代码评审要点

- [ ] 是否符合本规范（命名/注释/常量/模块化）
- [ ] 是否处理了边界与异常
- [ ] 是否有回归测试
- [ ] 是否影响其他模块（导入关系/共享状态/接口变更——改签名必须全项目搜调用方）
- [ ] 文档与日志是否同步更新

## 4. 日志规范

### 4.1 三层日志体系

| 层 | 位置 | 内容 | 轮转 |
|---|---|---|---|
| 开发日志 | `docs/开发日志/YYYY-MM-DD.md` | 每天做了什么、决策、问题、待办 | 按日新建，只追加 |
| 运行日志 | 各工程 `logs/项目名.log` | 程序运行日志（分级） | 每日轮转，保留 30 天 |
| 测试日志 | `test/logs/测试日志_YYYYMMDD_HHMMSS.log` | 测试执行过程与结果 | 带时间戳，不覆盖 |

### 4.2 运行日志规范（C++）

- 分级：`DEBUG`（函数出入口/参数）、`INFO`（关键状态变更）、`WARN`（可恢复异常）、`ERROR`（不可恢复，必须含上下文）。
- 格式：`[时间戳.毫秒] 级别 文件:行号 消息`。
- 实现：核心算法层用轻量日志宏（可静态开关），Web 层用 `pino`/`winston`；**禁止 `printf`/`console.log` 散落做调试**。
- 文件日志：`TimedRotatingFileHandler` 每日午夜轮转，`backupCount=30`。

### 4.3 开发日志模板

```markdown
# YYYY-MM-DD 开发日志

## 今日目标
- ...

## 完成事项
- [x] ...

## 关键决策（ADR）
- ADR-XXX：...

## 遇到的问题与解决
- 问题：... / 原因：... / 解决：...

## 测试情况
- 用例数 / 通过 / 失败：...

## 待办
- [ ] ...

## 关联文档
- 修改了哪些文档
```

## 5. 开发工作流（六角色协作）

```text
① 需求（PM）
   产品需求文档 → 需求评审
② 设计（架构师 + UI）
   架构设计 / ADR → 接口契约 → 设计评审
③ 开发（全栈工程师）
   编码（遵守规范）→ 编译检查 → 自测 → 提交
④ 测试（测试专家）
   用例设计 → 执行 → 测试日志 → 缺陷报告 → 回归
⑤ 文档（文档专家）
   同步更新文档与开发日志
⑥ 发布（全栈 + PM）
   构建产物 → 验收标准核对 → 发布记录
```

**每个里程碑结束**：六角色交付物齐备 + 评审通过，才可进入下一阶段。

## 6. 交付物清单与验收

| 发布 | 构建产物、发布记录 | 验收标准全部达成 |

## 7. 红线（不可违反）

1. 禁止修改 `Singan2_Lai_GBVE_SR_OLD` 目录内任何文件。
2. 禁止在不跑回归测试的情况下合并代码。
3. 禁止静默吞异常（`catch {}` / `catch(...)` 空块）。
4. 禁止硬编码魔法数字/路径/超时。
5. 禁止跳过文档与日志更新。
6. 禁止编造验证结果——对拍不一致必须记录差异并归因，不得"看起来差不多就通过"。
