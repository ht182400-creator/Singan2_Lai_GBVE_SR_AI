# 08_测试规范与用例管理

> 本文档定义 `Singan2_Lai_GBVE_SR_AI` 改造工程的测试标准（测试专家角色依据）。核心要求：**以测试专家视角全面覆盖，用例库用 JSON 数据驱动，测试日志带日期时间并分层，未通过标红，用例/JSON/文档三者一一对应**。

---

## 1. 测试原则

1. **不能只走一遍正常流程**：必须覆盖边界值、异常场景、并发/竞态。
2. **所有重要分支都要覆盖**：`if-else`、`try-catch`、`for-else`、`while-break`、`switch-case-default`。
3. **所有重要函数都要覆盖**：参数为空 / None / 非法值 / 合法值 / 边界值。
4. **用例三件套一一对应**：测试用例文档 ⇄ JSON 数据驱动文件 ⇄ 代码用例，输入/输出/期望/实际全部对齐。
5. **对拍测试**（本项目特有）：改造后的 `S2[1..32]` 输出必须与原版 exe 对同一数据逐项精确比对。

---

## 2. 测试分层

| 层 | 对象 | 工具/方式 | 触发时机 |
|---|---|---|---|
| L1 单元测试 | 单个函数/类（C_SI2、图像处理算子、解析器） | C++：Catch2 / GoogleTest；TS：Vitest/Jest | 每次提交 |
| L2 集成测试 | 管线（读文件 → 解析 → 特征计算 → 输出） | 数据驱动脚本 | 里程碑 |
| L3 对拍测试 | POC / Web / 优化后 vs 原版 exe | 对拍脚本 + 差异报告 | 每次改动 |
| L4 回归测试 | 全量用例库 | 自动回归脚本 | 每次合并前 |
| L5 性能测试 | 单枚处理耗时、批量吞吐 | 计时脚本 | 优化后 |

## 3. 测试用例库管理（JSON 数据驱动）

### 3.1 目录约定

```
test/
├── cases/                  # 用例定义（JSON 数据驱动）
│   ├── unit_*/             # 单元测试用例
│   ├── integration_*/      # 集成测试用例
│   └── duipai_*/           # 对拍测试用例
├── data/                   # 测试输入数据（.dat / 坐标文件 / 期望 S2）
├── logs/                   # 测试日志（带日期时间）
└── reports/                # 测试报告与缺陷记录
```

### 3.2 用例 JSON 模板

```json
{
  "caseId": "U-CSI2-AVG-001",
  "group": "unit/C_SI2",
  "title": "average_concentration2 合法区域计算",
  "priority": "P1",
  "category": "normal",
  "input": {
    "x": 10, "y": 20, "xx": 50, "yy": 60,
    "img": "data/sample_img_1.dat",
    "type": 0
  },
  "expected": {
    "return": 12345,
    "description": "与手工计算一致"
  },
  "notes": "覆盖正常输入"
}
```

### 3.3 用例分类（category）

| 分类 | 说明 | 必须覆盖 |
|---|---|---|
| `normal` | 正常合法输入 | ✅ |
| `boundary` | 边界值（空输入、0、MAX、超长字符串） | ✅ |
| `exception` | 异常场景（文件不存在、权限不足、网络断开、空指针） | ✅ |
| `branch` | 覆盖所有 if/switch 分支 | ✅ |
| `concurrency` | 并发/竞态（多线程、重复调用） | ✅（相关模块） |

### 3.4 用例与代码一一对应规则

1. 每个测试函数必须有对应 JSON 用例，`caseId` 唯一且稳定。
2. JSON 中的 `input` / `expected` 必须与代码测试内的输入/断言完全一致。
3. 测试用例文档（本文档下的用例清单）必须列出每个 `caseId` 的**输入/输出/期望值**。
4. 新增代码 → 新建用例；修改行为 → 更新用例 + 期望值；删除功能 → 删除用例。
5. **测试结果与期望值一一对应并详细记录**在测试日志中。

## 5. 测试日志规范

### 5.1 格式要求

- 文件名：`测试日志_YYYYMMDD_HHMMSS.log`（带日期和时间，不覆盖）。
- 内容分层：
  - `[INFO]` 用例开始、输入摘要
  - `[PASS]` 断言通过
  - `[FAIL]` 断言失败（**标红**：日志中输出 `[FAIL] ⚠` 或 ANSI 红色，报告中醒目）
  - `[SKIP]` 跳过
  - `[ERROR]` 用例执行异常（必须含上下文/栈）
- 汇总：末尾输出 `通过 X / 失败 Y / 跳过 Z`，失败用例列出 `caseId + 期望值 + 实际值 + 原因`。

### 5.2 对拍测试日志示例

```log
[2026-08-19 14:32:05.123][INFO ] 对拍开始: data/15_500AC_A.dat
[2026-08-19 14:32:05.220][INFO ] 原版 S2[1..32] 已加载 (32 项)
[2026-08-19 14:32:05.480][PASS ] S2[1]=1024  原=1024  新=1024
[2026-08-19 14:32:05.481][FAIL] ⚠ S2[7]=512  原=512   新=513  (差异: +1)
[2026-08-19 14:32:05.482][INFO ] 对拍结束: 通过 31/32, 失败 1/32
```

## 6. 对拍测试（项目核心）

### 6.1 流程

```text
同一枚 .dat
  ├─ 原版 exe → S2_original[1..32]
  └─ POC/Web → S2_new[1..32]
       ↓
 逐项比对（整型精确相等）
       ↓
 差异 → 写入缺陷表（索引/原值/新值/差值/归因/结论）
```

### 6.2 差异归因四类

| 归因 | 处理 |
|---|---|
| 解析偏移错误 | 修正解析逻辑 → 重跑回归 |
| 数值语义（溢出/定点） | WASM 无此问题；TS 用 `Math.imul`/`>>>0` 修正 |
| 原版自身 BUG | 记录为已知差异，另行评估是否修复 |
| 未定 | 冻结该数据，换数据再验，**不跳过** |

### 6.3 对拍用例数据要求

- 覆盖国家：优先 Euro / Chia / USA / Canada / HongKong。
- 覆盖数据形态：普通 `.dat`、SRU `.dat`（如存在）、带/不带文件头。
- 覆盖面额与方向：至少 A/B/C/D 四个方向各若干枚。

## 7. 缺陷管理

### 7.1 缺陷记录模板

```markdown
## BUG-XXX: <标题>
- 状态：新建 / 已确认 / 修复中 / 已验证 / 关闭 / 延后
- 优先级：P0 阻塞 / P1 高 / P2 中 / P3 低
- 发现日期：YYYY-MM-DD
- 复现步骤：...
- 期望行为：...
- 实际行为：...
- 关联用例：caseId
- 归因：解析 / 数值语义 / 原版 BUG / 未定
- 处理记录：...
```

### 7.2 缺陷闭环

`新建 → 确认 → 修复 → 回归验证 → 关闭`，每一步都必须有记录。P0 缺陷不修复不进入下一阶段。

## 11. jsdom 测试环境兜底（`web/src/test/setup.js`）与已知陷阱

> 2026-09-03 起前端测试 **38 文件 / 198 用例全绿**。以下是当时排查出的两类根因与环境兜底，新增组件/测试前必读。

### 11.1 jsdom 未实现 canvas → 必须 stub `getContext`

- **现象**：App 集成测试整组失败，报 `Not implemented: HTMLCanvasElement.prototype.getContext` 与
  `TypeError: Cannot set properties of null (setting 'dpr')`。
- **根因**：jsdom 不实现 canvas 2D，`getContext('2d')` 返回 null；ECharts/zrender 初始化时对 `ctx.dpr` 赋值即崩。
- **兜底**：`web/src/test/setup.js` 将 `HTMLCanvasElement.prototype.getContext` 替换为 2D 上下文桩
  （no-op 绘图方法 + `createImageData/getImageData` 返回空像素 + 可写的 `dpr` 等属性）。
  测试中断言 canvas 像素是无效的，断言行为/DOM 即可。

### 11.2 陷阱：组件内 state 命名遮蔽导入的函数

- **现象**：`App.jsx` 内 `const [logError, setLogError] = useState('')` **遮蔽**了从
  `debugLogger.js` 导入的 `logError` 函数 → 所有 catch 块 `logError(...)` 实际调用字符串 state，
  抛 `logError2 is not a function`（esbuild 对被遮蔽导入的重命名），且**只出现在异步 unhandled rejection 中**，测试仍显示"部分通过"，极具迷惑性。
- **后果**：错误处理路径 `stopBusy()` 被跳过 → 失败时 busy 指示卡死。
- **规则**：state / 局部变量命名禁止与导入函数同名（如 `logError`、`getLog`）；修复时统一改名为 `logViewError`。
- **排查法**：Vitest 报 `Unhandled Rejection` 即使测试 pass 也要追查；报错符号带数字后缀（`logError2`）通常是打包器重命名，说明存在遮蔽。

### 11.3 断言与实现同步

- 日志格式 2026-09-03 起为 `<ISO时间> [LEVEL] [MODULE] msg`，断言用正则 `/\[ERROR\] \[\w+\] fail/` 而非固定子串。
- 按钮文案对齐原版（如 `Combine` → `Graph (Combine)`）时，相关测试必须同轮更新（§10.3 三件套规则）。
