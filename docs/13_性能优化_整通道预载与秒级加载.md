# 性能优化：整通道预载与「秒载 1000 张」

> 适用范围：`Singan2_Lai_GBVE_SR_AI`（Web 重构工程）。
> 关联源码：`core/src/mariner_reader.cpp`、`server/server.cpp`、`web/src/api.js`、`web/src/App.jsx`、`web/src/components/ImagePane.jsx`。
> 关联文档：[优化与构建说明.md](./优化与构建说明.md)（§5 并发模型）、[11_模块功能同步方案_P0-P5.md](./11_模块功能同步方案_P0-P5.md)（P0 数据链路）。

## 0. 一句话结论

OLD MFC 之所以能「1 秒载入 1000 张」，是因为它把整个 `.dat` **常驻内存**，翻帧只是 `fseek`+`memcpy`（亚毫秒），**不走网络、不走 JSON、不 base64、不重建引擎**。
Web 版早期慢，是因为每翻一枚 record 都发一次 HTTP + 一次 base64 解码 + 一次 canvas 重绘。
本工程用「**整通道预载 + 浏览器内存切片 + TCP_NODELAY**」复刻了同一范式，并对照主流 Web 图像序列方案（OHIF / Napari / 视频帧播放器）做了选型。

## 1. 根因定位（实测，非猜测）

### 1.1 OLD 的加载机制（基准）

- 启动时 `fopen` 整个 `.dat`，全程 `FILE*` 常驻进程。
- 翻帧：`fseek(file, record * ONESIZE, SEEK_SET)` → `fread` 单枚 213KB → `memcpy` 13 个波段到显存/缓冲。
- 全部在进程内内存完成，逐帧切换亚毫秒级，与「网络/JSON/base64」完全无关。

### 1.2 Web 版早期逐帧慢的实测

用裸 socket（排除 Python `urllib` 客户端假象）对本地 server 实测：

| 端点 / 动作 | 实测延迟 | 说明 |
|---|---|---|
| `GET /health` | 1–2 ms | 服务端本身很快 |
| `POST /api/image`（单张 raw） | 7–10 ms | 单图取图 + 拷贝本就快 |
| `POST /api/small-image` | ~100 ms | 缩略图 |
| `POST /api/images/channel`（17MB 整通道） | **11 秒** | 瓶颈所在 |

### 1.3 服务端其实很快：11 秒是「测量客户端」的假象

在 `extract_wave_all` 内打了分段计时，server stderr 实测：

```text
[extract_wave_all] load=1116.4ms offsets=3.2ms copy=8.1ms count=1044 bytes=17088192
[extract_wave_all] load=0.0ms     offsets=0.1ms copy=10.8ms count=1044 bytes=17088192
```

- `load` 仅首次 1.1s（冷读 547MB 文件），之后命中 `load_file_cached` 为 **0ms**。
- `copy` 仅 **8–15ms**（17MB 像素 `memcpy`）。
- 即：**服务端算 17MB 只要 ~11ms**。

但早期用裸 socket 打 `/api/images/channel` 却测到 11 秒 —— **这不是服务端慢，而是测量用的 Python 客户端有 bug**：
它在接收循环里用 `data += chunk` 累加 17MB 响应体，而 Python `bytes` 不可变、`+=` 每次都整体复制，
4300 次累加形成 **O(n²)** 拷贝（17MB 累积约 37GB 内存搬移），在 Python 里正好耗 10+ 秒。
单张图只有 21KB（几次拷贝即完）所以测出来快，整通道 17MB 才暴露这个客户端缺陷。

用**正确的流式客户端**（把响应体直接流式落盘、不在内存里拼接）重测：

```text
channel Img1 #1: 108.4 ms   （#1 端到端含冷读文件 1.1s 已摊到 load 段）
channel Img1 #2:  79.3 ms
channel Img1 #3:  77.6 ms
bytes=17088192 与 recordCount*186*88 完全吻合
```

**结论：整通道 17MB 下发实测 ~80ms，服务端本身没有任何瓶颈。** 翻帧级的内存切片在此基础上再叠加亚毫秒级开销。

> 旁证：`curl` 早前只返回一个 27 字节错误（JSON 解析失败），说明当时 curl 的 body 未被正确解析（与服务端逻辑无关）；前端用 `fetch` + `JSON.stringify` 的同款请求已验证可正常取回 17MB。

## 2. 修复一：整通道预载端点 `/api/images/channel`

### 2.1 设计（对齐 OLD + 主流图像序列范式）

把一个波段的**全部 record 像素一次性下发**为二进制扁平缓冲，浏览器常驻为 `Uint8Array`，
之后翻帧只做内存切片（`subarray`），**零 HTTP、瞬时**。

- 请求：`POST /api/images/channel` `{ dat_path, wave }`，`wave` 如 `"Img1"`。
- 响应：`Content-Type: application/octet-stream`，body = `recordCount × width × height` 字节（u8）。
- 响应头：`X-Width` / `X-Height` / `X-Record-Count`（供前端重建帧步长）。
- 长度校验：`recordCount × 186 × 88` 必须等于实际字节数，否则判为文件损坏/越界返回 4xx。

### 2.2 服务端实现（`core/src/mariner_reader.cpp` → `extract_wave_all`）

```cpp
// 关键：用 memcpy 预分配缓冲，避免 Debug 下 std::vector::insert 的迭代器调试检查把 1044 次插入拖慢
std::vector<uint8_t> out(static_cast<size_t>(stride) * count);
for (int r = 0; r < count; ++r) {
    size_t rec_base = static_cast<size_t>(r) * side_off.block_size + side_off.pixel_off;
    std::memcpy(out.data() + static_cast<size_t>(r) * stride,
                file.data() + rec_base, static_cast<size_t>(stride));
}
```

`server.cpp` 中注册路由，把 `out` 用 `res.set_content(std::string(...), "application/octet-stream")` 发出，
并通过 `res.set_header("X-Width", ...)` 等回填三个头。

## 3. 传输层加固：`TCP_NODELAY`（防御性，非根因）

`server.cpp` 在 `svr.listen` 前加一行（已落地）：

```cpp
// 关闭 Nagle 算法：避免大响应体在某些网络路径（高延迟/特定回环栈）上因 Nagle+延迟ACK 相互等待而降速。
// 注：本机回环实测 17MB 下发 ~80ms 与此开关关系不大（真正的 11s 是测量客户端 O(n²) 缺陷，见 §1.3）；
// 但关闭 Nagle 对远端/高延迟部署是无副作用的稳妥加固，保留。
svr.set_tcp_nodelay(true);
```

**生效前提**：必须重编 `singan2_server`（见 §7）。本工程仅本地单机使用，关闭 Nagle 无副作用。

> 此加固同时惠及所有大响应体端点（含 `/api/upload` 4GB 上行不受影响；主要影响**下行**大块）。它不是本次 11s 的修复点，但保留无害。

## 4. 前端架构：通道缓存 + 内存切片

`web/src/App.jsx` 核心结构：

```jsx
const channelCacheRef = useRef(new Map());     // key: datPath::waveName -> { buf, width, height, count }
const channelInFlightRef = useRef(new Map());  // 去重：同一通道并发只下载一次
const CHANNEL_CACHE_LIMIT = 32;                // 超出按插入顺序淘汰最旧，防多文件/多波段无限占内存

const ensureChannel = useCallback(async (datPath, waveName) => { /* 命中缓存/在途则返回；否则 fetch /api/images/channel */ }, []);

const loadSideChannel = useCallback(async (datPath, record, waveName) => {
  const ch = await ensureChannel(datPath, waveName);
  const n = ch.width * ch.height;
  const gray = ch.buf.slice(record * n, record * n + n); // 仅切片该帧，不引用整缓冲
  return { width: ch.width, height: ch.height, gray, record, wave: waveName };
}, [ensureChannel, ...]);
```

`ImagePane.jsx` 的 `drawRawBuffer` 直接吃 `gray`（u8 行优先），不再走 base64 + canvas 重建。

## 5. 修复三：打开即并行预载全部 13 个原始波段

### 5.1 动机

`ensureChannel` 是**懒加载 + 缓存**：首次打开某波段要下载一次（~50ms），之后缓存命中瞬时。
但 OLD 是**所有波段全常驻**，连「第一次切波段」也瞬时。为完全对齐 OLD，新增开关。

### 5.2 范围

`VIEW_WAVES` 共 22 项，其中 `mode:'raw'` 的原始波段正好 **13 个**（Img1–Img6 + Img16–Img22），
合计 `13 × 186 × 88 × 1044 ≈ 221MB`。Img7–Img15 是中间计算波段（服务端无整通道存储），**不预载**。

### 5.3 实现（`web/src/App.jsx`）

```jsx
const [preloadAllWaves, setPreloadAllWaves] = useState(true); // 默认开，复刻 OLD 全文件常驻

const preloadAllWavesFor = useCallback((datPath) => {
  if (!datPath) return;
  const names = Object.values(VIEW_WAVES).filter((w) => w.mode === 'raw').map((w) => w.name);
  const tasks = names.map((n) => ensureChannel(datPath, n));    // 并行 13 个 fetch
  Promise.allSettled(tasks).then((res) => {
    const ok = res.filter((r) => r.status === 'fulfilled' && r.value).length;
    pushHistory(`预载 ${ok}/${names.length} 波段完成`);
  });
}, [ensureChannel, logInfo, pushHistory]);

// handleOpen 打开成功后（loadImages 之后，fire-and-forget，不阻塞 UI）：
if (preloadAllWaves) preloadAllWavesFor(p);
```

UI：Sub-Toolbar 右侧新增复选框「**打开即预载全部波段**」（`styles.css` 的 `.preload-all-waves`）。
勾选状态下中途打开文件也会立即对当前已开的 Data1/Data2 补预载。

### 5.4 影响面（对其它功能零侵入）

- 仅在「打开文件」这一处新增一个 fire-and-forget 预载调用；不改动 `loadImages`/`loadSideChannel`/`getImage` 等既有逻辑。
- 预载走的是与翻帧完全相同的 `ensureChannel` 缓存，命中后翻帧、换波段、Statistics 取样全部复用，无重复下载。
- 开关关闭时行为与优化前完全一致（首次切波段才下载）。
- 内存受 `CHANNEL_CACHE_LIMIT=32` 约束：13 波段 × 2 面板 = 26 < 32，不会触发淘汰。

## 6. 换波段到底快不快？

| 场景 | 首次打开该波段 | 之后切换回该波段 |
|---|---|---|
| 开关**关**（懒加载） | ~50ms 下载 17MB | 瞬时（内存切片） |
| 开关**开**（全预载） | 打开文件时已并行下完 | 瞬时（内存切片） |

结论：**开开关后，任意波段 / 任意帧翻动都达到 OLD 级别的零延迟**；关开关则首次切波段付一次 ~50ms（仍远快于早期逐帧方案）。

## 8. 互联网如何「秒级」处理大量数据（方法论 + 本工程选型）

核心原则只有一句：**绝不在每次交互时重传全量数据**。主流做法：

| 招式 | 说明 | 代表 | 本工程是否采用 |
|---|---|---|---|
| **A. 整序列/整文件预载到客户端内存** | 打开时拉一次，之后交互全内存切片 | 视频播放器、OHIF、Napari、游戏图集 | ✅ 采用（整通道预载） |
| **B. 按需取片段（HTTP Range / 字节服务）** | 只取要的那一块，相当于把 OLD 的 `fseek` 搬到网络 | 视频拖动、COG、S3 `Range:` | 本地单机无需（数据已在本地） |
| **C. 瓦片 + 金字塔（LOD / mipmap）** | 只传当前视野+缩放所需瓦片，缩略秒出、放大补高清 | DeepZoom、IIIF、OpenSeadragon、Google Maps | 本地单机过度设计，未采用 |
| **D. 二进制直传，不用 base64 裹 JSON** | base64 有 33% 膨胀 + 解析开销 | 所有现代二进制 API | ✅ 采用（octet-stream + Uint8Array） |
| **E. GPU / WebGL 常驻纹理** | 数据传一次到显存，平移缩放全 shader 免费算 | 地图/医学影像查看器 | 部分（canvas 直接吃 raw buffer） |
| **F. 传输层优化** | `TCP_NODELAY`、HTTP/2 多路复用、keep-alive、文本 gzip/brotli（已压缩二进制不压） | — | ✅ 采用 TCP_NODELAY |
| **G. 离主线程 & 零拷贝** | Web Worker 解码、`SharedArrayBuffer` 跨线程共享 | 大型影像工具 | 预载在后台 Promise，不卡 UI |

**本工程选型依据**：数据为**本地单机**（547MB 文件在本地），所以 A（整通道预载）+ D（二进制）+ F（TCP_NODELAY）是最优解——
这正是 OLD「文件常驻内存 + 指针直取」的本质，只是把「进程内内存」换成「浏览器 `Uint8Array`」。
B/C 更适合「数据在远端、带宽有限」的部署，对本地工具是过度设计。

| 指标 | OLD MFC | Web 优化前 | Web 优化后（开预载） |
|---|---|---|---|

## 10. 已知限制与后续

- 仅本地单机优化；若未来部署到远端，应改用 §8 的 B/C（Range / 瓦片）以节省带宽。
- `CHANNEL_CACHE_LIMIT=32` 对「多文件 × 多波段」长时间会话可能触发淘汰，届时翻帧会回退到 `getImage` 逐张（仍正确，仅稍慢）。
- 中间计算波段（Img7–Img15）暂不支持整通道预载（服务端无整通道存储），翻动走 `getImage` 逐张，属预期行为。

## 11. 关联优化：Make Graph 直方图「7s → 2s」（后续迭代）

整通道预载解决的是**翻帧/切波段**的延迟；而 **Make Graph（直方图）** 是另一条独立链路，同样经历了一次显著提速，详见 [优化与构建说明.md §1–§2.3](./优化与构建说明.md)。

### 11.1 问题

Make Graph 虽已并行化（`std::thread` 线程池），但每个 record 仍重复走完整图像重建：

```
extract_mm1_side()        // 提取该 record 13 个波段块
build_onebyte_images()    // 重建 13 张图
to_2byte()                // 把 22 个波段槽全转成 2 字节
gradient / niti / count
```

1044 枚 × 全量重建 ≈ **7s**（Debug 构建）。

### 11.2 优化

- 对原始波段（Img1..Img6、Img16..Img19）先 `extract_wave_all()` 一次性 `memcpy` 出全部 record 像素（约 17MB），避免每 record 重复 `extract_mm1_side()` + `build_onebyte_images()`。
- 新增 `make_graph_record_fast()`：只向 `ImageEngine` 装入**当前需要的单波段**，跳过 `to_2byte()` 对 22 槽的全量转换。
- 中间波段 Img7..Img15 保持原 `make_graph_record()` 路径。

### 11.3 实测（Debug，12 核，1044 枚，wave=Img1，Gra+Bin）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 前端 HTTP 总耗时 | 约 **7s** | 约 **2.0s** |
| 服务端纯计算 | — | **318ms**（0.30 ms/record） |

剩余 HTTP 时间主要是首次把 `.dat` 读入内存（LRU 缓存）；同文件再点 Make Graph 更快。切 **Release** 构建可再提速数倍。

### 11.4 讨论要点（易踩坑）

- **不要凭客户端测时给服务端定责**：早期把整通道 11s 归咎于 `TCP_NODELAY`/Nagle，复核后发现是测量用的 Python 客户端 `data += chunk` O(n²) 缺陷（§1.3）。服务端始终 ~80ms。
- **并行 ≠ 去掉冗余工作**：Make Graph 7s 的根因不是「没并行」，而是「每 record 重复 13 波段重建」；先减冗余再并行，收益远大于单纯加线程。
